\chapter{Results \& Evaluation}
\label{chap:ch5}

\par This chapter presents the evaluation of the MSA Detector system described in the preceding chapters. It begins with the selection and characterization of the datasets used for evaluation, followed by the presentation of the detection results across each dataset. The results are then discussed in the context of the detection methodology and qualitatively positioned relative to the related work surveyed in Chapter~\ref{chap:ch2}. The chapter concludes with an analysis of the limitations of the approach and the threats to validity of the evaluation.

\section{Dataset Selection}
\label{sec:dataset-selection}

\par The evaluation of the MSA Detector requires open-source Java-based microservice projects of sufficient size and complexity to exercise the detection pipeline. This section describes the criteria used for dataset selection and characterizes the selected projects.

\subsection{Selection Criteria}
\label{subsec:selection-criteria}

\par The following criteria were used to select evaluation datasets:

\begin{enumerate}
    \item The project must be primarily implemented in Java. The detection pipeline is optimised for Spring Boot conventions (Spring-specific annotations and configuration), but also accommodates other JVM-based microservice frameworks such as Jakarta EE/CDI (see Chapter~\ref{chap:ch3}).
    \item The project must contain at least three microservices, to enable meaningful detection of inter-service anti-patterns such as cyclic dependencies, chatty services and distributed monolith.
    \item The project must be publicly available on GitHub or GitLab, to ensure reproducibility of the evaluation.
    \item The project must use Maven or Gradle as a build system, as the microservice detection mechanism relies on the presence of \texttt{pom.xml}, \texttt{build.gradle} or \texttt{build.gradle.kts} files.
\end{enumerate}

\par At the smaller end of the scale, four projects serve as lightweight baselines. MicroservicesSocial\footnote{\url{https://github.com/sarbudragos/MicroserviceSocial}} is a mock social media application developed as a university course assignment, comprising 4 microservices and 1\,811 LOC. Despite its modest scope, it is useful as a minimal test case for detecting intra-service and configuration-related anti-patterns. NetworkDisk\footnote{\url{https://github.com/quhailong/NetworkDisk_Storage}} is a cloud storage system built on Spring Boot and Spring Cloud, consisting of 10 microservices with approximately 6\,729 LOC. It implements file upload, download and sharing functionality through a gateway-based architecture and is particularly relevant for exercising the API Versioning Absence and Nano Service detectors. PiggyMetrics\footnote{\url{https://github.com/sqshq/piggymetrics}} is a widely referenced personal finance management application built on Spring Cloud, comprising 8 microservices and approximately 4\,483 LOC. Organized around a gateway, a service registry and a centralized configuration server with several fine-grained domain services, it is a representative showcase of the canonical Spring Cloud reference architecture and exercises the ESB Misuse, API Versioning Absence and Nano Service detectors. piomin\footnote{\url{https://github.com/piomin/sample-spring-microservices-new}} is a compact sample Spring Cloud microservices project by Piotr Mi\'nkowski, consisting of 6 services and only approximately 1\,330 LOC. As the smallest codebase in the evaluation, it illustrates service discovery and gateway routing with minimal business logic, making it a useful stress test for the service-sizing and mediation-related detectors.

\par Four additional projects of medium scale were included to broaden the anti-pattern coverage. microservices-design-patterns\footnote{\url{https://github.com/rodrigorodrigues/microservices-design-patterns}} is a reference repository demonstrating common microservice design patterns, containing 16 Java-based microservices (out of a polyglot codebase also including JavaScript, Ruby and C\#) with approximately 18\,635 LOC. The project includes an API Gateway, making it a relevant candidate for versioning detection. A similar project, microservice-recruit\footnote{\url{https://github.com/stalary/microservice-recruit}}, is an intelligent recruitment platform built on Spring Cloud, comprising 8 microservices and 8\,280 LOC. It employs inter-service communication via Feign clients and a centralized gateway, making it a suitable candidate for detecting communication-related anti-patterns such as ESB Misuse, Cyclic Dependency and Wrong Cuts. Both NetworkDisk and microservice-recruit were also used as evaluation subjects in the cross-service code clone study by Zhao et~al.~\cite{10.1145/3524610.3527925}. The third medium-scale project, ftgo-application\footnote{\url{https://github.com/microservices-patterns/ftgo-application}}, is the reference microservices application accompanying Richardson's \textit{Microservices Patterns}~\cite{Richardson2018}, comprising 7 Spring Boot services and approximately 10\,508 LOC. Built around the Saga and CQRS patterns, it serves as a clean, well-engineered baseline against which the detection pipeline can be calibrated. The fourth medium-scale project, RuoYi-Cloud\footnote{\url{https://github.com/yangzongzhuan/RuoYi-Cloud}}, is a widely adopted Spring Cloud Alibaba enterprise rapid-development framework, comprising 8 microservices and approximately 27\,012 LOC. With a centralized gateway and Feign-based inter-service calls, it is representative of the enterprise scaffolding used in production by many development teams.

\par At the larger end, three production-grade and research-grade systems were selected to stress-test the detection pipeline at scale. Train-Ticket\footnote{\url{https://github.com/FudanSELab/train-ticket}} is a benchmark microservice system developed by the Software Engineering Lab at Fudan University, specifically designed for research on microservice architectures~\cite{XZhou2018}, and is also catalogued in the curated dataset of open-source microservice projects by Amoroso d'Aragona et~al.~\cite{10.1145/3643991.3644890}. It models a train ticket booking platform with 41 independently deployable Spring Boot services communicating via \texttt{RestTemplate}, totalling approximately 35\,762 LOC, and is notable for its complex inter-service dependency topology and fine-grained service boundaries. Site-Where\footnote{\url{https://github.com/sitewhere/sitewhere}} is an industrial-strength open-source IoT application enablement platform, consisting of 15 microservices with approximately 73\,854 LOC. Its centralized orchestration layer makes it a relevant candidate for ESB Misuse and God Service detection. Finally, mall-swarm\footnote{\url{https://github.com/macrozheng/mall-swarm}} is a Spring Cloud-based e-commerce platform widely used for industry training and adoption, comprising 7 microservices and approximately 86\,095 LOC. As the largest codebase in the evaluation, it exercises the pipeline against a feature-rich, gateway-and-Feign-based commerce system and triggers a broad mix of service-design, data-management and configuration anti-patterns.

\par The evaluation results show substantial variation in detector-derived architectural health across the selected projects. Health scores ranged from 40 to 83 (Figure~\ref{fig:health-scores}), suggesting that the detection pipeline can distinguish between projects with relatively few reported issues and those with a much higher concentration of reported anti-pattern candidates.

\par As shown in Figure~\ref{fig:antipattern-frequency}, API Versioning Absence was the most frequently detected anti-pattern, with 37 instances across nine projects, with NetworkDisk contributing 8 and microservice-recruit contributing 6 (as shown in the per-project breakdown in Table~\ref{tab:antipattern-distribution}). Nano Service was the second most common finding, appearing 23 times across nine projects. Hardcoded Endpoints was detected 15 times across six of the eleven evaluated projects. Chatty Service (4 instances, all in Train-Ticket) and ESB Misuse (9 instances across Site-Where, microservice-recruit, PiggyMetrics and piomin) appeared less frequently. God Service was detected in three projects (Site-Where, mall-swarm and RuoYi-Cloud, 4 instances total), and Shared Database was found in MicroservicesSocial, Train-Ticket and mall-swarm (3 instances total). Notably, the addition of NetworkDisk and microservice-recruit to the evaluation corpus activated detectors that had previously produced zero results: Cyclic Dependency was detected once in microservice-recruit, and Wrong Cuts was detected twice in the same project, providing evidence that a broader evaluation corpus can exercise a wider range of detection capabilities.

\par In terms of severity, the majority of detections (77\%) fall into the Medium category, with only a single Critical instance (Cyclic Dependency). No instances of Distributed Monolith were detected across the evaluated datasets. The absence of this anti-pattern is consistent with the communication topologies of the evaluated projects, which exhibit moderate inter-service coupling rather than the pervasive coupling that characterises a distributed monolith, so none of them crossed the detector's coupling and connectivity thresholds. Figure~\ref{fig:loc-vs-health} shows that project size (LOC) is not a reliable predictor of the health score in this sample: small projects can score poorly while large projects can maintain moderate scores, suggesting that detected architectural signals matter more than codebase scale alone.

\par A noteworthy observation is that several well-regarded reference systems received only moderate grades. The ftgo-application, the reference implementation accompanying Richardson's \textit{Microservices Patterns}~\cite{Richardson2018}, scored 75 (grade~C), with its deductions driven almost entirely by API Versioning Absence, and PiggyMetrics, a canonical Spring Cloud showcase, scored 71 (grade~C). This should not be read as evidence that these systems are poorly architected. Rather, it reflects a deliberate property of the composite score: it quantifies conformance to a specific catalogue of conventions and anti-patterns, and several exemplar projects intentionally forgo some of them.

\par API Versioning Absence is a particularly context-dependent signal, since many systems version their APIs at the gateway, through content negotiation, or via consumer-driven contracts rather than a URL path prefix, and some deliberately omit versioning during early development. As such, the detector flags the syntactic absence of a recognised versioning indicator, not the absence of any versioning strategy. That API Versioning Absence and Nano Service jointly account for 61\% of all detections, both at medium severity, further indicates that the score is shaped most strongly by the most prevalent and least severe findings. The category-based breakdown (Chapter~\ref{chap:ch3}, Section~\ref{subsec:health-score}) is what makes it actionable in this light: by attributing each deduction to a specific finding, it allows a reader to recognise that ftgo-application's grade stems from a single convention it has chosen not to adopt rather than from a structural defect, and to weigh that finding accordingly.

\subsection{Results Discussion}
\label{subsec:discussion-results}

\par This section presents the detailed detection results for a representative evaluated project, microservice-recruit, including the detected microservices, anti-pattern evidence, and the health score breakdown.

\subsubsection{microservice-recruit}
\label{subsubsec:results-microservice-recruit}

\par microservice-recruit is an intelligent recruitment platform built on Spring Cloud, comprising 8 microservices and approximately 8\,280 LOC, with inter-service communication carried out through Feign clients routed via a centralized gateway. Relative to its modest size, it is the most anti-pattern-dense project in the evaluation: the MSA Detector identified 13 anti-pattern instances across six distinct types. The communication- and coupling-related detectors were the most active. Two ESB Misuse instances were flagged for services acting as central mediators with disproportionately high betweenness centrality in the dependency graph, and two Wrong Cuts instances corresponded to bidirectional dependencies between service pairs, namely pf-recruit with pf-resume and pf-recruit with pf-user. A single Cyclic Dependency was detected, a closed loop in the inter-service call graph verified by manual inspection of the Feign client declarations. In addition, six API Versioning Absence instances were identified for controllers exposing REST endpoints without any version prefix in the URL path, alongside one Hardcoded Endpoint (a literal URL used in place of a discovery-resolved service name) and one Nano Service (a service below both the LOC and endpoint thresholds). Notably, microservice-recruit was the only project in the entire corpus to trigger the Cyclic Dependency and Wrong Cuts detectors, which made it especially useful for exercising the structural-coupling detectors.

\par The final health score of 40 (grade~F) illustrates how the composite score accumulates deductions across all four categories. The Anti-Patterns budget is fully exhausted: the penalties for 1~Cyclic Dependency instance (critical, $1 \times 8 = 8$), 2~ESB Misuse and 2~Wrong Cuts instances (high, $4 \times 5 = 20$), 6~API Versioning Absence instances ($6 \times 3 = 18$) and 1~Hardcoded Endpoint instance ($1 \times 3 = 3$) total~49, exceeding the 40-point budget, so $S_{\mathrm{ap}} = \max(0,\; 40 - 49) = 0$ (the single Nano Service is charged to Service Sizing instead, to avoid double counting). The Code Quality category is scored by smell density: the project's 260 code smells over 8\,280 LOC give 31.4 smells/KLOC, a penalty of $\min(20,\; \lfloor 20 \times 31.4 / 80 \rceil) = 8$, leaving $S_{\mathrm{cq}} = 12$ out of~20. The Architecture category incurs a 9-point penalty reflecting the structural coupling of its dependency graph, leaving $S_{\mathrm{arch}} = 16$ out of~25. Finally, the one Nano Service incurs a Service Sizing penalty of $\min(8,\; 1 \times 3) = 3$, leaving $S_{\mathrm{sz}} = 12$ out of~15. The composite is therefore $0 + 12 + 16 + 12 = 40$. Unlike a project whose deductions concentrate in a single category, microservice-recruit loses points in every dimension, which illustrates the multi-level nature of the scoring: architectural anti-patterns, structural coupling and code-level smell density jointly shape the final result.

\subsection{Manual Validation of Results}
\label{sec:manual-validation}

\par Manual inspection indicated that most of the 98 detected anti-pattern instances corresponded to plausible architectural concerns. The three Shared Database instances (in MicroservicesSocial, Train-Ticket and mall-swarm) were checked by confirming that the affected services declared identical datasource URLs in their configuration files. The Hardcoded Endpoints instances corresponded to literal URL strings embedded in \texttt{RestTemplate} or \texttt{WebClient} calls rather than service names resolved through a discovery mechanism. The API Versioning Absence instances were checked by inspecting the controller classes and verifying that none of their request mappings included a version prefix such as \texttt{/api/v1/}. The God Service detections were consistent with manual observation: the flagged services exceeded multiple structural thresholds in the Spoon-based analysis, indicating possible responsibility concentration.

\par The graph-derived findings were checked against the constructed dependency graph and the underlying client declarations. The four Chatty Service instances in Train-Ticket corresponded to service pairs with call counts exceeding the configured threshold, reflecting the system's fine-grained inter-service communication patterns as captured by static analysis. ESB Misuse was detected in Site-Where (3 instances), microservice-recruit (2 instances), PiggyMetrics (1 instance) and piomin (3 instances), identifying services acting as candidate central mediators with high betweenness centrality in the dependency graph. The Cyclic Dependency instance in microservice-recruit was checked by inspecting the inter-service call graph, and the two Wrong Cuts instances in the same project corresponded to bidirectional dependencies between service pairs.

\par The Nano Service detections presented the most nuanced cases. While all instances satisfied the configured thresholds (fewer than 500 lines of code and no more than 2 endpoints), some flagged modules may be internal utility or shared library modules that were detected as microservices by the build-file heuristic but are not independently deployable services. These cases represent a limitation of the automated service boundary detection rather than a flaw in the Nano Service detector itself. Distributed Monolith was the only anti-pattern type not detected across the evaluated datasets. Given the communication topologies of the evaluated projects, the absence of this anti-pattern is plausible rather than indicative of false negatives, although the possibility of missed detections due to unresolvable dynamic URLs or insufficient inter-service coupling cannot be ruled out.

\subsection{Practical Implications}
\label{subsec:practical-implications}

\par The results of this evaluation suggest several practical implications for development teams working with microservice architectures.

\par First, in a CI setting the REST API exposed by the backend (see Chapter~\ref{chap:ch4}, Section~\ref{subsec:rest-api}) could be used as a quality gate: a post-build step could submit the project for analysis and fail the pipeline if the health score falls below a configured threshold or a critical anti-pattern is detected, much as SonarQube enforces quality gates on code-level metrics. The current implementation would, however, need its thresholds calibrated to a team's own conventions before such a gate could safely block builds, since the defaults favour recall over precision.

\par Second, the diff feature (see Chapter~\ref{chap:ch4}, Section~\ref{subsec:analysis-diff}) compares two analysis runs of the same project: after a shared database anti-pattern is resolved, the re-analysis reports the resulting change in the health score and whether any new anti-patterns appeared. Third, because each finding stores the source snippet and the affected service list, a developer is shown the specific \texttt{@FeignClient} annotation or \texttt{RestTemplate} invocation that creates a cycle, together with the affected services and a remediation suggestion, rather than an abstract warning such as \textit{cyclic dependency detected}.

\section{Threats to Validity}
\label{sec:threats-validity}

\par This section identifies and discusses the threats to the validity of the evaluation, organized by the standard classification of construct, internal, external and conclusion validity.

\subsection{Construct Validity}
\label{subsec:construct-validity}

\par Construct validity concerns whether the metrics and thresholds used in the detection pipeline accurately measure the intended concepts.

\par The nano service detection criterion (Equation~\ref{eq:nano-service-detection}) uses the conjunction of LOC and endpoint count as a proxy for \textit{insufficient operational justification}. However, a low LOC service may still perform a critical function (e.g., an authentication service that delegates to an external identity provider), and a service with few endpoints may encapsulate complex internal logic. The combination of both metrics mitigates this risk but does not completely eliminate it.

\par The god service detection criterion (Equation~\ref{eq:god-service-detection}) treats the presence of a God Class, identified from structural metrics such as size and class cohesion, as a proxy for \textit{excessive responsibility concentration}. While a class that exceeds several structural thresholds is a strong indicator, a service may handle multiple responsibilities without any single class crossing those thresholds if the responsibilities are distributed across many small classes. Conversely, a single large domain model may exceed the thresholds without the service genuinely spanning multiple business domains.

\par The coupling coefficient (Equation~\ref{eq:coupling-coeff-dm}) measures the ratio of actual to possible inter-service dependencies. Although a high coupling coefficient suggests tight coupling, it does not account for the directionality or nature of the dependencies. A system where all services depend on a single shared library service may have a high coupling coefficient without exhibiting the characteristics of a distributed monolith.

\par The chatty service call count derived from \texttt{@FeignClient} interfaces counts one unit per declared method. This is a static proxy for runtime call frequency rather than a measurement of it, since a method may be invoked many times or not at all during execution. The count therefore reflects the breadth of a service's remote interface rather than the actual volume of traffic it generates.

\par The Code Quality category scores code smell density as reported by DesigniteJava. Because DesigniteJava is run separately on each service, it cannot observe usages that cross service boundaries, so classes that are referenced only by other services, such as shared data transfer objects or Feign client interfaces, are frequently reported as Unutilized Abstraction. This inflates the smell density of the affected services, so the resulting code quality penalty should be read as an upper bound rather than an exact measure.

\par The ESB Misuse detector applies a single mediator threshold ($\theta_m = 0.4$) uniformly to three differently-scaled signals, i.e. the connection ratios, the volume-based mediator ratio and the normalised betweenness centrality, and flags a service when any one of them is exceeded (Equation~\ref{eq:esb-decision}). In small dependency graphs the volume-based ratio in particular is easily satisfied, so more than one service in the same system can be reported as a central mediator, even though the anti-pattern by definition describes a single dominant hub. The disjunctive decision rule therefore favours recall over precision, and the reported ESB Misuse instances are better interpreted as candidate mediators warranting inspection rather than as mutually exclusive hubs. This is consistent with the multiple ESB Misuse instances observed in some of the smaller evaluated projects (Table~\ref{tab:antipattern-distribution}).

\par The composite health score formula (Equation~\ref{eq:health-score}) aggregates multiple quality dimensions into a single numeric value. Any such aggregation involves a loss of information, and the chosen penalty weights may not reflect the relative importance of different anti-patterns in all contexts. The category-based breakdown provided by \texttt{HealthScoreCalculator} partially addresses this by preserving per-category scores.

\subsection{Internal Validity}
\label{subsec:internal-validity}

\par Internal validity concerns whether the results are attributable to the detection methodology rather than to confounding factors such as implementation bugs or procedural errors.

\par The detectors are executed sequentially and independently, as each detector receives the same input (the project and its microservices) and produces results without knowledge of other detectors' output. This independence ensures that the order of detector execution does not influence outcomes. The pipeline does, however, share data across stages through the database, as the code smells saved by the DesigniteJava integration are later read when computing the code quality category of the health score. If the code smell persistence step and the consuming step are not correctly isolated transactionally, intermittent visibility issues could affect the computed score.

\par The DesigniteJava results were parsed from CSV output files using a parser that locates columns by their header names rather than by fixed positions, which tolerates reordered or version-specific column layouts. Substantial changes in DesigniteJava's output format could still cause parsing errors, although the parser includes defensive checks for malformed lines and missing columns.

\subsection{External Validity}
\label{subsec:external-validity}

\par External validity concerns the generalizability of the results beyond the specific projects and configuration used in this evaluation.

\par The evaluation uses open-source sample and demonstration projects, which may differ from real enterprise systems in several ways. Enterprise systems tend to be larger in scale (hundreds of services, millions of LOC), employ more diverse communication mechanisms (gRPC, message queues, event streams), and evolve over years with multiple teams contributing. The anti-pattern distributions observed in the evaluated sample projects may not reflect those of enterprise systems.

\par The evaluated projects may have been designed as teaching examples and may intentionally contain (or intentionally lack) certain anti-patterns. For instance, a tutorial project may use a shared database for simplicity, which the detector would correctly flag, but this design choice may be intentional rather than accidental. Conversely, well-maintained sample projects may exhibit fewer anti-patterns than typical enterprise systems where architectural debt accumulates over time \cite{Taibi2018}.

\par The results are specific to Java microservice projects (predominantly Spring Boot) and do not generalize to microservice systems built with other languages. Polyglot microservice systems, i.e. where services are implemented in different languages, are increasingly common in practice, and the current tool cannot analyze non-Java services within such systems.

\subsection{Conclusion Validity}
\label{subsec:conclusion-validity}

\par Conclusion validity concerns the reliability and reproducibility of the conclusions drawn from the evaluation.

\par The manual validation of detection results was performed by a single person (the author of this dissertation), introducing a potential bias. A different reviewer might classify borderline cases differently, particularly for anti-patterns with subjective elements such as \texttt{nano service} (where the threshold between an appropriately small service and an excessively small one is context-dependent) or \texttt{god service} (where the boundary between a feature-rich service and an over-responsible one is debatable).

\par The detection results are deterministic for a given project and set of thresholds: running the tool twice on the same codebase with the same configuration produces identical results. However, different threshold configurations can lead to substantially different detection counts, which could affect the conclusions about anti-pattern prevalence and reported detection behaviour.

\section{Summary}
\label{sec:ch5-summary}

\par This chapter presented the evaluation of the MSA Detector system on a set of open-source Java-based microservice projects. The evaluation aimed to characterize the tool's detection behaviour and the kinds of architectural anti-pattern candidates it reports on diverse microservice codebases.

\par Eleven projects were selected for evaluation, meeting the criteria of being Java Spring Boot applications with multiple microservices. The selected projects included a total of 130 detected microservices across approximately 274\,000 lines of code, and represented various domains including IoT platforms, ticket booking, cloud storage, e-commerce, intelligent recruitment, food-delivery, personal finance management, enterprise application development and learning projects. The detection pipeline identified 98 anti-pattern instances across nine distinct anti-pattern types, with varying implications for architectural quality.

\par The results showed that the MSA Detector can identify candidate instances of common microservice anti-patterns such as shared databases, API versioning absences, and nano services. The health scores provided a useful summary metric for comparing detector-derived architectural health, with detailed breakdowns available for deeper analysis.

\par The evaluation also identified several limitations and threats to validity, including the restriction to Java Spring Boot projects, the reliance on static analysis, and the limited representativeness of the evaluation datasets. These factors may affect the generalizability of the results, and caution is advised in interpreting the findings as definitive measures of architectural quality.

\par Overall, the evaluation provided positive indications of the MSA Detector's capabilities, while also highlighting areas for improvement and further research. The next chapter will conclude this dissertation with a summary of contributions, reflections on the research process, and suggestions for future work in the area of microservice architecture analysis and improvement.
