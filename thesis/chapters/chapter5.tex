\chapter{Results \& Evaluation}
\label{chap:ch5}

\par This chapter presents the evaluation of the MSA Detector system described in the preceding chapters. It begins with the selection and characterization of the datasets used for evaluation, followed by the presentation of the detection results across each dataset. The results are then discussed in the context of the detection methodology and compared against related work. The chapter concludes with an analysis of the limitations of the approach and the threats to validity of the evaluation.

\section{Dataset Selection}
\label{sec:dataset-selection}

\par The evaluation of the MSA Detector requires open-source Java-based microservice projects of sufficient size and complexity to exercise the detection pipeline. This section describes the criteria used for dataset selection and characterizes the selected projects.

\subsection{Selection Criteria}
\label{subsec:selection-criteria}

\par The following criteria were used to select evaluation datasets:

\begin{enumerate}
    \item The project must be implemented in Java using the Spring Boot framework, as the detection pipeline relies on Spring-specific annotations and configuration conventions (see Chapter~\ref{chap:ch3}).
    \item The project must contain at least three microservices, to enable meaningful detection of inter-service anti-patterns such as cyclic dependencies, chatty services and distributed monolith.
    \item The project must be publicly available on GitHub or GitLab, to ensure reproducibility of the evaluation.
    \item The project must use Maven or Gradle as a build system, as the microservice detection mechanism relies on the presence of \texttt{pom.xml}, \texttt{build.gradle} or \texttt{build.gradle.kts} files.
\end{enumerate}

\textbf{MicroservicesSocial} is an application available at \url{https://github.com/sarbudragos/MicroserviceSocial}. It consists of 4 microservices and uses Maven as its build system. The project is a mock social media application written for a university course assignment. It is relatively small, with a total of 1\,811 LOC, and serves as a baseline test case for the detection pipeline.

\textbf{microservices-design-patterns} is an application available at \url{https://github.com/rodrigorodrigues/microservices-design-patterns}. The repository contains microservices written in multiple languages, including Java, JavaScript, Ruby and C\#; of these, 16 Java-based microservices were analyzed, including \textit{user-service} and \textit{person-service}. The project uses Maven as its build system, employs a shared database by design, and includes an API Gateway.

\textbf{Site-Where} is an application available at \url{https://github.com/sitewhere/sitewhere}. It is an industrial-strength open-source application enablement platform for the Internet of Things (IoT), consisting of 15 microservices with approximately 73\,854 LOC. The system uses a microservice architecture with inter-service communication patterns and a centralized orchestration layer, making it a relevant candidate for detecting ESB Misuse and God Service anti-patterns.

\textbf{Genie} is an application available at \url{https://github.com/Netflix/genie}. Genie is a distributed Big Data orchestration service developed by Netflix, designed to provide job management and execution capabilities for distributed computing frameworks such as Hadoop and Spark. The system consists of 11 microservices with approximately 117\,512 LOC. As a production-grade Netflix OSS project, Genie provides a realistic test of the detection pipeline against a well-engineered, large-scale codebase.

\textbf{Train-Ticket} is an application available at \url{https://github.com/FudanSELab/train-ticket}. It is a benchmark microservice system developed by the Software Engineering Lab at Fudan University, specifically designed for research on microservice architectures. The system models a train ticket booking platform and consists of 41 independently deployable Spring Boot services communicating via REST calls and \texttt{RestTemplate}. With approximately 35\,762 LOC, it provides a realistic microservice topology with inter-service dependencies, shared data stores and fine-grained service boundaries.

\textbf{Apollo-Config} is an application available at \url{https://github.com/apolloconfig/apollo}. Apollo is a reliable, production-grade distributed configuration management system developed by Ctrip (Trip.com Group), designed for microservice configuration management scenarios. The system consists of 11 modules detected as microservices, with approximately 85\,806 LOC. Unlike the smaller demonstration projects in this evaluation, Apollo is a mature, widely deployed system used in production environments, providing a realistic test of the detection pipeline against a well-engineered, real-world codebase.

\textbf{NetworkDisk} is an application available at \url{https://github.com/quhailong/NetworkDisk_Storage}. It is a cloud storage system built on Spring Boot and Spring Cloud, consisting of 10 microservices with approximately 6\,729 LOC. The project implements file upload, download and sharing functionality through a gateway-based architecture, making it a relevant candidate for detecting API Versioning Absence and Nano Service anti-patterns.

\textbf{microservice-recruit} is an application available at \url{https://github.com/stalary/microservice-recruit}. It is an intelligent recruitment platform built on a Spring Cloud microservice architecture, consisting of 8 microservices with approximately 8\,280 LOC. The system employs inter-service communication via Feign clients and a centralized gateway, making it a useful test case for detecting communication-related anti-patterns such as ESB Misuse, Cyclic Dependency and Wrong Cuts.

The selected projects vary substantially in both size and structure, ranging from small teaching-oriented systems to large enterprise-scale and production-grade codebases, which provides a useful basis for evaluating the detection pipeline under different conditions. Several of the selected projects, notably NetworkDisk and microservice-recruit, were also used as evaluation subjects in the cross-service code clone study by Zhao et~al.~\cite{10.1145/3524610.3527925}, which provided additional confidence in their suitability as representative microservice systems.

\par Hardcoded Endpoints was the most frequently detected anti-pattern, with 45 instances across all eight evaluated projects, of which 26 originated from Train-Ticket alone. API Versioning Absence was the second most common finding, with 24 instances across six projects, with NetworkDisk contributing 8 and microservice-recruit contributing 6. Nano Service appeared 20 times across six projects. Chatty Service (4 instances, all in Train-Ticket) and ESB Misuse (5 instances across Site-Where and microservice-recruit) appeared less frequently. God Service was detected in two projects (Site-Where and Genie, 3 instances total), and Shared Database was found in both MicroservicesSocial and Train-Ticket. Notably, the addition of NetworkDisk and microservice-recruit to the evaluation corpus activated detectors that had previously produced zero results: Cyclic Dependency was detected once in microservice-recruit, and Wrong Cuts was detected twice in the same project, demonstrating that a broader evaluation corpus can exercise a wider range of detection capabilities. No instances of Distributed Monolith were detected across the evaluated datasets. The absence of this anti-pattern is consistent with the communication topologies of the evaluated projects and aligns with the empirical observation by Taibi and Lenarduzzi that service-sizing and configuration-related issues are more prevalent than severe system-level coupling problems in practice \cite{Taibi2018}.

\par To illustrate how the composite health score is constructed from the four-category decomposition described in Chapter~\ref{chap:ch3}, Section~\ref{subsec:health-score}, consider the breakdown for Train-Ticket (score~52, grade~D). The Anti-Patterns category (budget~40) incurred penalties for 4~Chatty Service instances ($4 \times 5 = 20$), 4~Nano Service instances ($4 \times 3 = 12$), 26~Hardcoded Endpoint instances ($26 \times 3 = 78$), and 1~Shared Database instance ($1 \times 5 = 5$), for a total penalty of~115; clamped to the category budget, $S_{\mathrm{ap}} = \max(0,\; 40 - 115) = 0$. The Service Sizing category (budget~15) accumulated a nano penalty of $\min(8,\; 4 \times 3) = 8$, yielding $S_{\mathrm{sz}} = \max(0,\; 15 - 8) = 7$. Code Quality and Architecture both received perfect scores ($S_{\mathrm{cq}} = 20$, $S_{\mathrm{arch}} = 25$) because DesigniteJava did not produce code smell reports for this project and the coupling coefficient was below the 0.1 penalty threshold. The total is therefore $H = 0 + 20 + 25 + 7 = 52$. This decomposition shows that Train-Ticket's low score is driven primarily by the high volume of anti-pattern deductions (particularly Hardcoded Endpoints and Chatty Services), while its architectural coupling structure is clean. The fact that Code Quality and Architecture scored perfectly across the evaluated projects reflects a limitation of the evaluation corpus rather than a flaw in the scoring model: in a production setting with richer DesigniteJava output and more complex dependency graphs, these categories would contribute meaningful differentiation.


\subsection{Results Discussion}
\label{subsec:discussion-results}

\par This section presents the detailed detection results for an evaluated project, e.g. MicroservicesSocial, including the detected microservices, anti-pattern evidence, and the health score breakdown.

\subsubsection{MicroservicesSocial}
\label{subsubsec:results-microservicessocial}

\par MicroservicesSocial is the smallest project in the evaluation, consisting of four microservices with a combined codebase of only 1\,811 lines of code. The project was developed as part of a university course assignment by a colleague and models a simplified social media platform. Its four services, a user service, a notification service, a post service and an API gateway, communicate via REST calls using \texttt{RestTemplate}. Because the project was built as a learning exercise rather than a production system, it provides a useful baseline for examining how the detection pipeline behaves on a small, structurally simple codebase. Despite its modest size, the MSA Detector identified five anti-pattern instances across four distinct anti-pattern types, which demonstrates that even small systems can exhibit a meaningful number of architectural issues.

\par The most architecturally significant finding was the detection of a Shared Database anti-pattern: two of the four services were configured with identical datasource URLs pointing to the same PostgreSQL database, meaning that they share a physical data store rather than owning their data independently. This is a common shortcut in student and prototype projects, where setting up separate databases for each service adds infrastructure complexity that is not central to the learning objective. The detector also flagged two Nano Service instances, corresponding to services whose line count and endpoint count both fell below the configured thresholds. It is rather unsurprising that some services qualify as nano services, in a project that only has four services with fewer than 500 lines per service on average. A single Hardcoded Endpoint was detected in a \texttt{RestTemplate} call that used a literal URL string rather than a service name resolved through a discovery mechanism and one API Versioning Absence instance was identified for a controller that exposes REST endpoints without any version prefix in the URL path. No cyclic dependencies, chatty services, god services, or distributed monolith indicators were detected which is consistent with the project's simple, linear communication topology.

\par The overall health score for MicroservicesSocial was 77 out of 100, corresponding to a letter grade of C. The deductions were distributed across the anti-patterns category (shared database and nano service penalties). While a score of 77 places the project in the lower-middle range of evaluated datasets, the result should be interpreted in context: the anti-patterns present are largely attributable to the project's educational nature and small scale rather than to fundamental architecture missteps. A developer receiving this report would have a clear list of improvements, such as externalizing database configuration per service, introducing a service registry and adding API version prefixes, which could raise the health score significantly with modest effort.


\subsection{Manual Validation of Results}
\label{sec:manual-validation}

\par The majority of the 106 detected anti-pattern instances were confirmed as genuine issues upon manual inspection. The two Shared Database instances (in MicroservicesSocial and Train-Ticket) were verified by confirming that the affected services declared identical datasource URLs in their configuration files. The Hardcoded Endpoints instances corresponded to actual literal URL strings embedded in \texttt{RestTemplate} or \texttt{WebClient} calls rather than service names resolved through a discovery mechanism; Train-Ticket accounted for 26 of these, consistent with its architecture of many services communicating via direct HTTP calls. The API Versioning Absence instances were confirmed by inspecting the controller classes and verifying that none of their request mappings included a version prefix such as \texttt{/api/v1/}. The God Service detections were consistent with manual observation: the flagged services contained DesigniteJava-detected God Classes or exceeded multiple structural thresholds in the Spoon-based fallback analysis, indicating excessive responsibility concentration. The four Chatty Service instances in Train-Ticket corresponded to service pairs with call counts exceeding the configured threshold, reflecting the system's fine-grained inter-service communication patterns. ESB Misuse was detected in Site-Where (3 instances) and microservice-recruit (2 instances), identifying services acting as central mediators with high betweenness centrality in the dependency graph. The Cyclic Dependency instance in microservice-recruit was verified by inspecting the inter-service call graph, and the two Wrong Cuts instances in the same project corresponded to services exhibiting cross-boundary Feature Envy or bidirectional dependencies.

\par The Nano Service detections presented the most nuanced cases. While all instances satisfied the configured thresholds (fewer than 500 lines of code and no more than 2 endpoints), some flagged modules may be internal utility or shared library modules that were detected as microservices by the build-file heuristic but are not independently deployable services. These cases represent a limitation of the automated service boundary detection rather than a flaw in the Nano Service detector itself. Distributed Monolith was the only anti-pattern type not detected across the evaluated datasets. Given the communication topologies of the evaluated projects, the absence of this anti-pattern is plausible rather than indicative of false negatives, although the possibility of missed detections due to unresolvable dynamic URLs or insufficient inter-service coupling cannot be ruled out.

\subsection{Practical Implications}
\label{subsec:practical-implications}

\par The results of this evaluation suggest several practical implications for development teams working with microservice architectures.

\par First, the MSA Detector can be integrated into existing development workflows to provide continuous architectural quality monitoring. The REST API exposed by the backend (see Chapter~\ref{chap:ch4}, Section~\ref{subsec:rest-api}) enables programmatic integration into CI/CD pipelines: a post-build step could submit the project for analysis and fail the pipeline if the health score falls below a configurable threshold or if critical anti-patterns are detected. This is analogous to how tools such as SonarQube enforce quality gates on code-level metrics.

\par Second, the composite health score provides a quantifiable metric that teams can track over time. The diff feature (see Chapter~\ref{chap:ch4}, Section~\ref{subsec:analysis-diff}) enables teams to measure the concrete impact of refactoring efforts: when a team resolves a shared database anti-pattern, the subsequent re-analysis quantifies the health score improvement and confirms that no new anti-patterns were introduced.

\par Third, the evidence-based reporting approach, i.e. attaching source code snippets and affected service lists to each detected anti-pattern, reduces the effort required for developers to understand and act on the findings. Rather than receiving an abstract warning such as \textit{cyclic dependency detected}, the developer is shown the specific \texttt{@FeignClient} annotation or \texttt{RestTemplate} invocation that creates the cycle, along with the affected services and a remediation suggestion.

\section{Threats to Validity}
\label{sec:threats-validity}

\par This section identifies and discusses the threats to the validity of the evaluation, organized by the standard classification of construct, internal, external and conclusion validity.

\subsection{Construct Validity}
\label{subsec:construct-validity}

\par Construct validity concerns whether the metrics and thresholds used in the detection pipeline accurately measure the intended concepts.

\par The nano service detection criterion (Equation~\ref{eq:nano-service-detection}) uses the conjunction of LOC and endpoint count as a proxy for \textit{insufficient operational justification}. However, a low LOC service may still perform a critical function (e.g., an authentication service that delegates to an external identity provider), and a service with few endpoints may encapsulate complex internal logic. The combination of both metrics mitigates this risk but does not completely eliminate it.

\par The god service detection criterion (Equation~\ref{eq:god-service-detection}) uses God Class frequency as a proxy for \textit{excessive responsibility concentration}. While the presence of multiple God Classes is a strong indicator, a service may handle multiple responsibilities without triggering God Class detection if the responsibilities are distributed across many small classes. Conversely, a service with a single large domain model may trigger God Class detection without genuinely spanning multiple business domains.

\par The coupling coefficient (Equation~\ref{eq:coupling-coeff-dm}) measures the ratio of actual to possible inter-service dependencies. Although a high coupling coefficient suggests tight coupling, it does not account for the directionality or nature of the dependencies. A system where all services depend on a single shared library service may have a high coupling coefficient without exhibiting the characteristics of a distributed monolith.

\par The composite health score formula (Equation~\ref{eq:health-score}) aggregates multiple quality dimensions into a single numeric value. Any such aggregation involves a loss of information, and the chosen penalty weights may not reflect the relative importance of different anti-patterns in all contexts. The category-based breakdown provided by \texttt{HealthScoreCalculator} partially addresses this by preserving per-category scores.

\subsection{Internal Validity}
\label{subsec:internal-validity}

\par Internal validity concerns whether the results are attributable to the detection methodology rather than to confounding factors such as implementation bugs or procedural errors.

\par The detectors are executed sequentially and independently; each detector receives the same input (the project and its microservices) and produces results without knowledge of other detectors' output. This independence ensures that the order of detector execution does not influence outcomes. However, the detectors share data through the database: code smells saved by the DesigniteJava integration are queried by the God Service detector. If the code smell persistence step and the anti-pattern detection step are not correctly isolated transactionally, intermittent visibility issues could affect God Service detection accuracy.

\par The DesigniteJava results were parsed from CSV output files using a line-by-line parser that matches expected column positions. Changes in DesigniteJava's output format across versions could cause parsing errors, although the parser includes defensive checks for malformed lines.

\subsection{External Validity}
\label{subsec:external-validity}

\par External validity concerns the generalizability of the results beyond the specific projects and configuration used in this evaluation.

\par The evaluation uses open-source sample and demonstration projects, which may differ from real enterprise systems in several ways. Enterprise systems tend to be larger in scale (hundreds of services, millions of LOC), employ more diverse communication mechanisms (gRPC, message queues, event streams), and evolve over years with multiple teams contributing. The anti-pattern distributions observed in the evaluated sample projects may not reflect those of enterprise systems.

\par The evaluated projects may have been designed as teaching examples and may intentionally contain (or intentionally lack) certain anti-patterns. For instance, a tutorial project may use a shared database for simplicity, which the detector would correctly flag, but this design choice may be intentional rather than accidental. Conversely, well-maintained sample projects may exhibit fewer anti-patterns than typical enterprise systems where architectural debt accumulates over time \cite{Taibi2018}.

\par The results are specific to Java Spring Boot projects and do not generalize to microservice systems built with other languages or frameworks. Polyglot microservice systems, i.e. where services are implemented in different languages, are increasingly common in practice, and the current tool cannot analyze non-Java services within such systems.

\subsection{Conclusion Validity}
\label{subsec:conclusion-validity}

\par Conclusion validity concerns the reliability and reproducibility of the conclusions drawn from the evaluation.

\par The manual validation of detection results was performed by a single person (the author of this dissertation), introducing a potential bias. A different reviewer might classify borderline cases differently, particularly for anti-patterns with subjective elements such as \texttt{nano service} (where the threshold between an appropriately small service and an excessively small one is context-dependent) or \texttt{god service} (where the boundary between a feature-rich service and an over-responsible one is debatable).

\par The detection results are deterministic for a given project and set of thresholds: running the tool twice on the same codebase with the same configuration produces identical results. However, different threshold configurations can lead to substantially different detection counts, which could affect the conclusions about anti-pattern prevalence and detection accuracy.

\section{Summary}
\label{sec:ch5-summary}

\par This chapter presented the evaluation of the MSA Detector system on a set of open-source Java-based microservice projects. The evaluation aimed to assess the tool's effectiveness in detecting architectural anti-patterns and providing actionable insights to improve microservice design quality.

\par Eight projects were selected for evaluation, meeting the criteria of being Java Spring Boot applications with multiple microservices. The selected projects included a total of 116 detected microservices across approximately 350\,000 lines of code, and represented various domains including IoT platforms, big data orchestration, configuration management, ticket booking, cloud storage, intelligent recruitment and learning projects. The detection pipeline identified 106 anti-pattern instances across nine distinct anti-pattern types, with varying implications for architectural quality.

\par The results showed that the MSA Detector could effectively identify common microservice anti-patterns such as shared databases, API versioning absences, and nano services. The health scores provided a useful summary metric for assessing the overall architectural quality, with detailed breakdowns available for deeper analysis.

\par The evaluation also identified several limitations and threats to validity, including the restriction to Java Spring Boot projects, the reliance on static analysis, and the limited representativeness of the evaluation datasets.
