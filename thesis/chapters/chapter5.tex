\chapter{Results \& Evaluation}
\label{chap:ch5}

\par This chapter presents the evaluation of the MSA Detector system described in the preceding chapters. It begins with the selection and characterization of the datasets used for evaluation, followed by the presentation of the detection results across each dataset. The results are then discussed in the context of the detection methodology and compared against related work. The chapter concludes with an analysis of the limitations of the approach and the threats to validity of the evaluation.

\section{Dataset Selection}
\label{sec:dataset-selection}

\par The evaluation of the MSA Detector requires open-source Java-based microservice projects of sufficient size and complexity to exercise the detection pipeline. This section describes the criteria used for dataset selection and characterizes the selected projects.

\subsection{Selection Criteria}
\label{subsec:selection-criteria}

\par The following criteria were used to select evaluation datasets:

\begin{enumerate}
    \item The project must be implemented in Java using the Spring Boot framework, as the detection pipeline relies on Spring-specific annotations and configuration conventions (see Chapter~\ref{chap:ch3}).
    \item The project must contain at least three microservices, to enable meaningful detection of inter-service anti-patterns such as cyclic dependencies, chatty services and distributed monolith.
    \item The project must be publicly available on GitHub or GitLab, to ensure reproducibility of the evaluation.
    \item The project must use Maven or Gradle as a build system, as the microservice detection mechanism relies on the presence of \texttt{pom.xml}, \texttt{build.gradle} or \texttt{build.gradle.kts} files.
\end{enumerate}

\par At the smaller end of the scale, two projects serve as lightweight baselines. MicroservicesSocial\footnote{\url{https://github.com/sarbudragos/MicroserviceSocial}} is a mock social media application developed as a university course assignment, comprising 4 microservices and 1\,811 LOC. Despite its modest scope, it is useful as a minimal test case for detecting intra-service and configuration-related anti-patterns. NetworkDisk\footnote{\url{https://github.com/quhailong/NetworkDisk_Storage}} is a cloud storage system built on Spring Boot and Spring Cloud, consisting of 10 microservices with approximately 6\,729 LOC. It implements file upload, download and sharing functionality through a gateway-based architecture and is particularly relevant for exercising the API Versioning Absence and Nano Service detectors.

\par Four additional projects of medium scale were included to broaden the anti-pattern coverage. microservices-design-patterns\footnote{\url{https://github.com/rodrigorodrigues/microservices-design-patterns}} is a reference repository demonstrating common microservice design patterns, containing 16 Java-based microservices (out of a polyglot codebase also including JavaScript, Ruby and C\#) with approximately 18\,635 LOC. The project includes an API Gateway, making it a relevant candidate for versioning detection. A similar project, microservice-recruit\footnote{\url{https://github.com/stalary/microservice-recruit}}, is an intelligent recruitment platform built on Spring Cloud, comprising 8 microservices and 8\,280 LOC. It employs inter-service communication via Feign clients and a centralized gateway, making it a suitable candidate for detecting communication-related anti-patterns such as ESB Misuse, Cyclic Dependency and Wrong Cuts. Both NetworkDisk and microservice-recruit were also used as evaluation subjects in the cross-service code clone study by Zhao et~al.~\cite{10.1145/3524610.3527925}. The third medium-scale project, ftgo-application\footnote{\url{https://github.com/microservices-patterns/ftgo-application}}, is the reference microservices application accompanying Richardson's \textit{Microservices Patterns}~\cite{Richardson2018}, comprising 7 Spring Boot services and approximately 10\,508 LOC. Built around the Saga and CQRS patterns, it serves as a clean, well-engineered baseline against which the detection pipeline can be calibrated. The fourth medium-scale project, RuoYi-Cloud\footnote{\url{https://github.com/yangzongzhuan/RuoYi-Cloud}}, is a widely adopted Spring Cloud Alibaba enterprise rapid-development framework, comprising 8 microservices and approximately 27\,012 LOC. With a centralized gateway and Feign-based inter-service calls, it is representative of the enterprise scaffolding used in production by many development teams.

\par At the larger end, three production-grade and research-grade systems were selected to stress-test the detection pipeline at scale. Train-Ticket\footnote{\url{https://github.com/FudanSELab/train-ticket}} is a benchmark microservice system developed by the Software Engineering Lab at Fudan University, specifically designed for research on microservice architectures~\cite{XZhou2018}, and is also catalogued in the curated dataset of open-source microservice projects by Amoroso d'Aragona et~al.~\cite{10.1145/3643991.3644890}. It models a train ticket booking platform with 41 independently deployable Spring Boot services communicating via \texttt{RestTemplate}, totalling approximately 35\,762 LOC, and is notable for its complex inter-service dependency topology and fine-grained service boundaries. Site-Where\footnote{\url{https://github.com/sitewhere/sitewhere}} is an industrial-strength open-source IoT application enablement platform, consisting of 15 microservices with approximately 73\,854 LOC. Its centralized orchestration layer makes it a relevant candidate for ESB Misuse and God Service detection. Finally, mall-swarm\footnote{\url{https://github.com/macrozheng/mall-swarm}} is a Spring Cloud-based e-commerce platform widely used for industry training and adoption, comprising 7 microservices and approximately 86\,095 LOC. As the largest codebase in the evaluation, it exercises the pipeline against a feature-rich, gateway-and-Feign-based commerce system and triggers a broad mix of service-design, data-management and configuration anti-patterns.

\par The evaluation results show substantial variation in architectural quality across the selected projects. Health scores ranged from 39 to 83 (Figure~\ref{fig:health-scores}), indicating that the detection pipeline was able to distinguish between projects with relatively few issues and those with a much higher concentration of anti-patterns. As shown in Figure~\ref{fig:antipattern-frequency}, Hardcoded Endpoints was the most frequently detected anti-pattern, with 43 instances across eight of the nine evaluated projects, of which 26 originated from Train-Ticket alone (visually evident in the heatmap in Figure~\ref{fig:antipattern-heatmap}). API Versioning Absence was the second most common finding, with 31 instances across seven projects, with NetworkDisk contributing 8 and microservice-recruit contributing 6. Nano Service appeared 15 times across seven projects. Chatty Service (4 instances, all in Train-Ticket) and ESB Misuse (5 instances across Site-Where and micro\-service-recruit) appeared less frequently. God Service was detected in three projects (Site-Where, mall-swarm and RuoYi-Cloud, 4 instances total), and Shared Database was found in MicroservicesSocial, Train-Ticket and mall-swarm (3 instances total). Notably, the addition of NetworkDisk and microservice-recruit to the evaluation corpus activated detectors that had previously produced zero results: Cyclic Dependency was detected once in microservice-recruit, and Wrong Cuts was detected twice in the same project, demonstrating that a broader evaluation corpus can exercise a wider range of detection capabilities. In terms of severity (Figure~\ref{fig:severity-distribution}), the majority of detections (82\%) fall into the Medium category, with only a single Critical instance (Cyclic Dependency). No instances of Distributed Monolith were detected across the evaluated datasets. The absence of this anti-pattern is consistent with the communication topologies of the evaluated projects and aligns with the empirical observation by Taibi and Lenarduzzi that service-sizing and configuration-related issues are more prevalent than severe system-level coupling problems in practice \cite{Taibi2018}. Figure~\ref{fig:loc-vs-health} shows that project size (LOC) is not a reliable predictor of health score: small projects can score poorly while large ones can maintain moderate quality, suggesting that architectural decisions matter more than codebase scale.

\par To illustrate how the composite health score accumulates deductions, consider Train-Ticket (final score~40, grade~F). Its Anti-Patterns budget is fully exhausted: the penalties for 4~Chatty Service instances ($4 \times 5 = 20$), 26~Hardcoded Endpoint instances ($26 \times 3 = 78$) and 1~Shared Database instance ($1 \times 5 = 5$) total~103, far exceeding the 40-point budget, so $S_{\mathrm{ap}} = \max(0,\; 40 - 103) = 0$ (Nano Service instances are charged to Service Sizing instead, to avoid double counting). The four Nano Services incur a Service Sizing penalty of $\min(8,\; 4 \times 3) = 8$, leaving $S_{\mathrm{sz}} = 7$ out of~15. With DesigniteJava enabled, the Code Quality category contributes a further deduction: scored by smell density, the project's 1\,565 code smells leave $S_{\mathrm{cq}} = 8$ out of~20. These deductions --- led by the 26 hardcoded endpoints and 4 chatty-service pairs in the anti-pattern category --- account for Train-Ticket's low composite of~40, with code-smell density a secondary but non-trivial contributor. The example illustrates the multi-level nature of the scoring, in which architectural anti-patterns and code-level smell density jointly shape the final result.

\subsection{Results Discussion}
\label{subsec:discussion-results}

\par This section presents the detailed detection results for an evaluated project, e.g. MicroservicesSocial, including the detected microservices, anti-pattern evidence, and the health score breakdown.

\subsubsection{MicroservicesSocial}
\label{subsubsec:results-microservicessocial}

\par MicroservicesSocial is the smallest project in the evaluation (4 services, 1\,811 LOC), developed as a university course assignment modeling a simplified social media platform. Despite its modest size, the MSA Detector identified five anti-pattern instances across four types: one Shared Database (two services configured with identical PostgreSQL datasource URLs), two Nano Services (services below both LOC and endpoint thresholds), one Hardcoded Endpoint (a \texttt{RestTemplate} call using a literal URL), and one API Versioning Absence. No cyclic dependencies, chatty services, god services or distributed monolith indicators were detected, consistent with the project's simple communication topology.

\par The health score was 83/100 (grade B), with deductions concentrated in the anti-patterns category. \subsection{Practical Implications}
\label{subsec:practical-implications}

\par The results of this evaluation suggest several practical implications for development teams working with microservice architectures.

\par First, the MSA Detector can be integrated into existing development workflows to provide continuous architectural quality monitoring. The REST API exposed by the backend (see Chapter~\ref{chap:ch4}, Section~\ref{subsec:rest-api}) enables programmatic integration into CI/CD pipelines: a post-build step could submit the project for analysis and fail the pipeline if the health score falls below a configurable threshold or if critical anti-patterns are detected. This is analogous to how tools such as SonarQube enforce quality gates on code-level metrics.

\par Furthermore, the composite health score provides a quantifiable metric that teams can track over time. The diff feature (see Chapter~\ref{chap:ch4}, Section~\ref{subsec:analysis-diff}) enables teams to measure the concrete impact of refactoring efforts: when a team resolves a shared database anti-pattern, the subsequent re-analysis quantifies the health score improvement and confirms that no new anti-patterns were introduced. In addition, the evidence-based reporting approach, i.e. attaching source code snippets and affected service lists to each detected anti-pattern, reduces the effort required for developers to understand and act on the findings. Rather than receiving an abstract warning such as \textit{cyclic dependency detected}, the developer is shown the specific \texttt{@FeignClient} annotation or \texttt{RestTemplate} invocation that creates the cycle, along with the affected services and a remediation suggestion.

\section{Threats to Validity}
\label{sec:threats-validity}

\par This section identifies and discusses the threats to the validity of the evaluation, organized by the standard classification of construct, internal, external and conclusion validity.

\subsection{Construct Validity}
\label{subsec:construct-validity}

\par Construct validity concerns whether the metrics and thresholds used in the detection pipeline accurately measure the intended concepts.

\par The nano service detection criterion (Equation~\ref{eq:nano-service-detection}) uses the conjunction of LOC and endpoint count as a proxy for \textit{insufficient operational justification}. However, a low LOC service may still perform a critical function (e.g., an authentication service that delegates to an external identity provider), and a service with few endpoints may encapsulate complex internal logic. The combination of both metrics mitigates this risk but does not completely eliminate it.

\par The god service detection criterion (Equation~\ref{eq:god-service-detection}) uses God Class frequency as a proxy for \textit{excessive responsibility concentration}. While the presence of multiple God Classes is a strong indicator, a service may handle multiple responsibilities without triggering God Class detection if the responsibilities are distributed across many small classes. Conversely, a service with a single large domain model may trigger God Class detection without genuinely spanning multiple business domains.

\par The coupling coefficient (Equation~\ref{eq:coupling-coeff-dm}) measures the ratio of actual to possible inter-service dependencies. Although a high coupling coefficient suggests tight coupling, it does not account for the directionality or nature of the dependencies. A system where all services depend on a single shared library service may have a high coupling coefficient without exhibiting the characteristics of a distributed monolith.

\par The composite health score formula (Equation~\ref{eq:health-score}) aggregates multiple quality dimensions into a single numeric value. Any such aggregation involves a loss of information, and the chosen penalty weights may not reflect the relative importance of different anti-patterns in all contexts. The category-based breakdown provided by \texttt{HealthScoreCalculator} partially addresses this by preserving per-category scores.

\subsection{Internal Validity}
\label{subsec:internal-validity}

\par Internal validity concerns whether the results are attributable to the detection methodology rather than to confounding factors such as implementation bugs or procedural errors.

\par The detectors are executed sequentially and independently, as each detector receives the same input (the project and its microservices) and produces results without knowledge of other detectors' output. This independence ensures that the order of detector execution does not influence outcomes. However, the detectors share data through the database, such as code smells saved by the DesigniteJava integration are queried by the God Service detector. If the code smell persistence step and the anti-pattern detection step are not correctly isolated transactionally, intermittent visibility issues could affect God Service detection accuracy.

\par The DesigniteJava results were parsed from CSV output files using a line-by-line parser that matches expected column positions. Changes in DesigniteJava's output format across versions could cause parsing errors, although the parser includes defensive checks for malformed lines.

\subsection{External Validity}
\label{subsec:external-validity}

\par External validity concerns the generalizability of the results beyond the specific projects and configuration used in this evaluation.

\par The evaluation uses open-source sample and demonstration projects, which may differ from real enterprise systems in several ways. Enterprise systems tend to be larger in scale (hundreds of services, millions of LOC), employ more diverse communication mechanisms (gRPC, message queues, event streams), and evolve over years with multiple teams contributing. The anti-pattern distributions observed in the evaluated sample projects may not reflect those of enterprise systems.

\par The evaluated projects may have been designed as teaching examples and may intentionally contain (or intentionally lack) certain anti-patterns. For instance, a tutorial project may use a shared database for simplicity, which the detector would correctly flag, but this design choice may be intentional rather than accidental. Conversely, well-maintained sample projects may exhibit fewer anti-patterns than typical enterprise systems where architectural debt accumulates over time \cite{Taibi2018}.

\par The results are specific to Java Spring Boot projects and do not generalize to microservice systems built with other languages or frameworks. Polyglot microservice systems, i.e. where services are implemented in different languages, are increasingly common in practice, and the current tool cannot analyze non-Java services within such systems.

\subsection{Conclusion Validity}
\label{subsec:conclusion-validity}

\par Conclusion validity concerns the reliability and reproducibility of the conclusions drawn from the evaluation.

\par The manual validation of detection results was performed by a single person (the author of this dissertation), introducing a potential bias. A different reviewer might classify borderline cases differently, particularly for anti-patterns with subjective elements such as \texttt{nano service} (where the threshold between an appropriately small service and an excessively small one is context-dependent) or \texttt{god service} (where the boundary between a feature-rich service and an over-responsible one is debatable).

\par The detection results are deterministic for a given project and set of thresholds: running the tool twice on the same codebase with the same configuration produces identical results. However, different threshold configurations can lead to substantially different detection counts, which could affect the conclusions about anti-pattern prevalence and detection accuracy.

\section{Summary}
\label{sec:ch5-summary}

\par This chapter presented the evaluation of the MSA Detector system on a set of open-source Java-based microservice projects. The evaluation aimed to assess the tool's effectiveness in detecting architectural anti-patterns and providing actionable insights to improve microservice design quality.

\par Nine projects were selected for evaluation, meeting the criteria of being Java Spring Boot applications with multiple microservices. The selected projects included a total of 116 detected microservices across approximately 269\,000 lines of code, and represented various domains including IoT platforms, ticket booking, cloud storage, e-commerce, intelligent recruitment, food-delivery, enterprise application development and learning projects. The detection pipeline identified 108 anti-pattern instances across nine distinct anti-pattern types, with varying implications for architectural quality.

\par The results showed that the MSA Detector could effectively identify common microservice anti-patterns such as shared databases, API versioning absences, and nano services. The health scores provided a useful summary metric for assessing the overall architectural quality, with detailed breakdowns available for deeper analysis.

\par The evaluation also identified several limitations and threats to validity, including the restriction to Java Spring Boot projects, the reliance on static analysis, and the limited representativeness of the evaluation datasets. These factors may affect the generalizability of the results, and caution is advised in interpreting the findings as definitive measures of architectural quality.

\par Overall, the evaluation provided positive indications of the MSA Detector's capabilities, while also highlighting areas for improvement and further research. The next chapter will conclude this dissertation with a summary of contributions, reflections on the research process, and suggestions for future work in the area of microservice architecture analysis and improvement.
