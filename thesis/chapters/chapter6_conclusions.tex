\chapter{Conclusions \& Future Work}
\label{conclusions}

\section{Summary of Contributions}
\label{sec:summary-contributions}

\par This dissertation presented the MSA Detector, an automated static analysis tool for detecting architectural anti-patterns in Java-based microservice systems. The tool implements a multi-level analysis pipeline that combines intra-service code analysis, performed by integrating DesigniteJava as an external subprocess together with Spoon-based structural metrics, with inter-service dependency analysis based on Spoon's Abstract Syntax Tree traversal and graph algorithms. God Service detection, for example, evaluates six structural metrics including Tight Class Cohesion to identify classes that concentrate too many responsibilities, while Chatty Service detection combines dependency-graph edge analysis with source-based scanning for HTTP client patterns. Thus, the tool uses both code-level indicators and structural metrics as signals for architectural-level anti-patterns, bridging a gap that existing tools address only partially.

\par The detection pipeline covers ten anti-patterns organized across four architectural dimensions: service design (Nano Service, God Service), communication (Chatty Service, Cyclic Dependency, Hardcoded Endpoints, ESB Misuse), data management (Shared Database) and deployment and coupling (Distributed Monolith, API Versioning Absence, Wrong Cuts). Each detector is implemented as a pluggable Strategy component with configurable thresholds externalized in the application configuration. Every detected anti-pattern is accompanied by source code snippets extracted during analysis, affected service lists and remediation guidance, so that a developer can act on a finding directly from the report.

\par A further contribution is the automated microservice boundary detection mechanism, which identifies services by scanning for build files and filtering out non-service modules through an exclusion heuristic, without the running system or the manual curation of service boundaries that existing tools tend to rely on. The composite health score quantifies overall architectural quality on a 0-100 scale with letter grading and decomposes it into four weighted categories: anti-pattern severity, code quality, architectural coupling, and service sizing, each with an itemized list of deductions. A built-in analysis diff feature compares successive analysis runs, so a change in the health score after a refactoring can be attributed to the specific findings that were resolved or introduced. The tool is delivered as a web application with a RESTful API, an Angular-based dashboard and Docker-based deployment, supporting both interactive use and programmatic integration into existing CI/CD pipelines.

\par The evaluation on eleven open-source microservice projects, encompassing 130 detected microservices and approximately 274\,000 lines of code, provided evidence that the MSA Detector can identify architectural anti-patterns through static analysis, with manual inspection confirming that the majority correspond to plausible architectural concerns. A total of 98 anti-pattern instances were detected across nine distinct types, including ESB Misuse, Chatty Service, Cyclic Dependency and Wrong Cuts, exercising detectors that target inter-service communication topology and cross-boundary coupling.

\par Viewed as a whole, the main outcome of this work is not the individual detectors in isolation, but the demonstration that code-level smell signals and dependency-graph signals can be combined into a single health score and surfaced together in a developer-facing workflow, with each finding traceable back to the source code that triggered it.

\section{Limitations}
\label{sec:limitations}

\par Several limitations of the approach should be acknowledged. The detection pipeline is restricted to Java-based microservice systems and is optimised for Spring Boot conventions. Although it also accommodates other JVM frameworks such as Jakarta EE/CDI, detection coverage is highest for Spring-based projects, and services written in other languages cannot be analyzed. The tool relies exclusively on static analysis and does not incorporate runtime data from distributed tracing or actual call frequency measurements, meaning that anti-patterns which manifest only at runtime may not be detected accurately. The automated microservice detection heuristic, while effective for multi-module Maven and Gradle projects, may produce false positives for non-service submodules such as shared libraries, and may miss services that do not follow conventional directory structures. Similarly, the inter-service dependency resolution cannot handle dynamically constructed URLs resolved through external configuration services such as Spring Cloud Config, potentially leaving some dependencies undetected.

\par The composite health score uses a linear deduction formula with fixed penalty weights that have not been empirically validated across a large corpus of projects, and the default detection thresholds were chosen based on values reported in the literature and reasonable engineering judgement rather than systematic calibration. Finally, the evaluation was conducted on eleven open-source projects of varying size and maturity, which may not be fully representative of enterprise microservice systems in terms of scale, complexity and the distribution of anti-patterns encountered in production environments.

\section{Future Work}
\label{sec:future-work}

\par Several directions for future research and development emerge from this work. The most impactful extension would be multi-language support, enabling the analysis of microservices written in Python, Go, .NET or Node.js. A language-agnostic dependency graph could be constructed from infrastructure artifacts such as Docker Compose files, Kubernetes manifests or API gateway configurations, while language-specific analyzers would handle intra-service code smell detection for each supported ecosystem.

\par The anti-pattern catalog could be extended with additional patterns not yet covered, such as timeout misconfiguration in inter-service calls and the absence of an API gateway. A more incremental step in the same direction would be to collect manually labelled findings from repeated use of the tool and use them to calibrate the detection thresholds or to rank findings by their likelihood of being relevant, rather than treating every detection as equally important. Larger-scale machine learning, such as training classifiers on labelled datasets of microservice projects or applying graph neural networks to the dependency graph, would only become realistic once enough labelled data of this kind exists, which is currently the main obstacle.

\section{Concluding Remarks}
\label{sec:concluding-remarks}

\par The evaluation in this dissertation suggests that static analysis can provide useful early feedback on microservice architecture, particularly when each finding carries source-level evidence and is presented as a candidate for review rather than a definitive verdict. This matters because manual architectural reviews do not scale to systems with dozens or hundreds of services and thousands of inter-service dependencies, while the consequences of undetected anti-patterns, such as cascading failures, deployment friction and mounting maintenance costs, can be severe. Combining code-level smell detection with architectural-level dependency analysis allows this feedback to be produced without a running system or manual configuration of service boundaries.

\par The MSA Detector offers developers and architects a practical means of gaining early stage visibility into architectural debt, tracking quality improvements over time through the composite health score and analysis diff features. While the current implementation is limited to Java Spring Boot systems, the underlying methodology is applicable to microservice systems regardless of language or framework and provides a foundation upon which future extensions can build.
